# 개선 과정 기록: 무엇을 고민했고 어떻게 결정했나

팀 프로젝트가 끝난 뒤 SpoKeeper를 개인적으로 이어서 개선한 과정을 고민, 판단 근거, 결정 순서로 정리했다. 마지막 절에서 처음 파이프라인과 지금 파이프라인을 비교한다.

## 1. 모델을 바꾸면 얼마나 나아지는가

- **고민:** 팀 프로젝트는 solar-pro2 하나로 모든 단계를 돌렸다. 새 모델(solar-pro3, solar-pro4)로 바꾸면 좋아질 것 같았지만, 느낌이 아니라 숫자로 확인하고 싶었다.
- **판단 근거:** 『주홍색의 연구』 14장에 대해 장별 정답 세트를 만들고, 누적 7개 위치에서 인물·관계를 채점했다.
- **결정:** solar-pro3과 solar-pro4만 비교했다. pro4는 핵심 관계 재현율이 30.7%에서 63.0%로 올랐고, 틀린 관계가 20개에서 2개로 줄었다. 그래서 기본 모델을 pro4로 정했다.
- **남은 것:** 정답 세트를 사람이 전수 검토하지 않았다. 관계 재현율이 63%에서 멈춘 이유가 정답이 너무 넓어서인지 모델이 놓쳐서인지는 아직 모른다.

## 2. 멀티 에이전트를 다 써야 하나

- **고민:** 단계가 많을수록 느리고 비싸다. 각 단계가 정말 정확도에 기여하는지 의문이었다.
- **판단 근거:** 같은 추출 결과를 전체 파이프라인과 경량 파이프라인(필터, 동일 인물 병합, 근거 검증)에 각각 통과시켜 점수를 비교했다.
- **결정:** 경량 파이프라인은 점수가 같거나 높았고 LLM 호출은 약 1/4이었다. 문제는 단계 수가 아니라 추출 단계의 관계 재현율이라는 결론을 내렸다.

## 3. solar-decide를 어디에 쓸까

- **고민:** solar-decide는 질문을 주면 확률을 돌려주는 분류 API다. LLM이 JSON을 생성하는 것보다 안정적일 것 같아서, 쓸 수 있는 곳을 찾고 싶었다.
- **시도 1: 동일 인물 판정을 Decide로 대체.** 정확도 이득이 없었고, 단계 시간 합계가 25초에서 467초로 늘었다.
- **시도 2: 일반 지칭 판별만 Decide에 맡기기(hybrid).** 경량 파이프라인과 점수가 같았다.
- **결정:** 당시에는 기본값에 넣지 않고 선택 옵션으로 남겼다. 나중에 6절에서 제자리를 찾았다. Decide는 두 이름이 같은지 판단하는 것보다, 이름 하나가 인물인지 묻는 데 맞았다.

## 4. 리마인드와 간접 누출 판정

- **고민:** 리마인드(여기까지의 줄거리 요약)는 꼭 필요한 기능이라고 봤다. 간접 누출 판정 에이전트는 직접 스포일러뿐 아니라 암시나 복선까지 잡으려고 설계했고, solar-pro4라면 이걸 잘 잡아낼 거라고 기대했다.
- **판단 근거:** 먼저 리마인드가 앞으로 나올 내용을 미리 말하는지 확인했다. 그다음 판정 에이전트가 무엇을 바꾸는지 비교했다.
- **결과:** 리마인드 104줄에서 미리 말하는 스포일러는 없었다. 판정 에이전트는 모델마다 12줄을 고쳤는데, pro4의 11장 위치에서는 오히려 복선 표현을 덧붙였다.
- **결정:** 리마인드는 유지하고 판정 에이전트는 뺐다. 시험 코드와 결과는 기록으로 남겼다.

## 5. 팀 저장소와 개인 연구 분리

- **고민:** 팀 결과물은 그대로 기록으로 두고, 개인 연구는 따로 보여 주고 싶었다.
- **결정:** 팀 커밋 기록 없이 별도 저장소를 만들고, README에서 팀 프로젝트가 출처임을 밝혔다. DB(Supabase) 없이 돌아가는 로컬 모드를 추가해서 누구나 실행해 볼 수 있게 했다.

## 6. 일반 지칭 필터가 책 하나에 맞춰져 있었다

- **고민:** pro4로 책 전체를 분석해 보니 "대머리 독수리", "이주민 무리", "홈즈와 와트슨", 다른 소설의 탐정(뒤팽), 벽에 쓰인 단어(RACHE→"레이첼")가 인물로 남았다. 원인을 보니 기존 필터는 단어 목록 규칙이었고, 목록에 특정 소설의 단어가 섞여 있었다. 다른 책이 오면 대처할 수 없는 구조였다.
- **판단 근거:** 규칙 대신 solar-decide에 질문 4개를 하게 했다. 개인 이름인가, 한 명인가, 이야기 속 인물인가, 실재하는 존재인가. 저장된 결과에 적용해 보니 문제 항목이 모두 걸렸다.
- **덧붙여 시험한 것:** 인물 설명을 경계선마다 쌓아서 판단하면 나아질지 시험했다. 점수는 거의 움직이지 않았고, 질문 문구를 바꾼 효과가 더 컸다.
- **결정:** 단어 규칙을 파이프라인에서 빼고 질문 기반 검사로 바꿨다. 규칙은 기록으로만 남겼다.

## 7. 역할 호칭을 어떻게 이름과 연결할까

- **고민:** "예언자"는 브리감 영, "순찰 경관"은 존 랜스의 다른 이름일 수 있다. 그냥 지우면 관계가 사라진다. 기존 동일 인물 병합은 이름이 겹치는 인물과 최근 8명만 후보로 봐서, 이름이 전혀 다른 호칭은 비교조차 되지 않았다.
- **아이디어:** 후보를 이름이 아니라 설명으로 좁히자. 그다음 본문 근거로 확정하자.
- **시험 결과:** 설명으로 후보를 좁히는 것은 잘 됐다. 그런데 본문 확인 단계에서 두 건이 틀렸다.
  - "소여라는 노파"가 범인과 연결됐다. 근거는 홈즈의 추리 문장이었다. 실제로 이 인물의 정체는 끝까지 밝혀지지 않는다.
  - "하숙집 아주머니"(화자의 하숙집 주인)가 샤르팡티에 부인(피살자의 하숙집 주인)과 연결됐다. 같은 역할이라 설명이 비슷했을 뿐 다른 사람이다.
- **선택지:** 정확도 우선(확실한 것만 연결), 추출 단계로 옮기기, 두 모델의 동의를 요구하기, 지우지 않고 화면에서만 숨기기를 비교했다.
- **결정:** 정확도 우선을 택했다. 근거 문장 안에 호칭과 후보 이름이 함께 나올 때만 연결한다. 틀린 연결은 오정보이자 스포일러가 되지만, 연결을 놓쳐서 잃는 관계는 호칭당 0~2개로 작았다. 다시 돌린 결과 예언자→브리감 영만 연결되고 틀린 연결은 0건이었다.

## 처음과 지금 비교

| 항목 | 처음 (팀 프로젝트) | 지금 |
|---|---|---|
| 추출·생성 모델 | solar-pro2 | solar-pro4 (비교 실험으로 결정) |
| 인물이 아닌 항목 거르기 | 단어 목록 규칙 (특정 책 단어 포함, 한국어만) | solar-decide 질문 4개 (책과 무관) |
| 역할 호칭 | 처리 없음 (남거나, 규칙에 걸리면 삭제) | 본문 한 문장에 호칭과 이름이 함께 있으면 연결, 아니면 삭제 |
| 연결 시점 | 해당 없음 | 확인된 경계선부터만 적용 (이전 위치에 정체가 새지 않음) |
| 동일 인물 병합 | LLM | LLM (유지) |
| 근거 검증 | 있음 | 있음 (유지) |
| 리마인드 | 있음 | 있음 (유지) |
| 간접 누출 판정 | 있음 | 제거 (시험에서 이득 없음, 복선 추가 사례) |
| LLM 후처리 단계 | 4단계 | 3단계 + solar-decide 검사 |
| 실행 환경 | Docker + Supabase + Redis | 기존 구성 + DB 없는 로컬 모드 |
| 근거 | 감 | 정답 세트 채점, 리마인드 시험, 실제 책 사례 검증 |

같은 책에서 정답 세트로 측정한 추출 품질(7개 위치 합산):

| | 핵심 인물 재현율 | 핵심 관계 재현율 | 정밀도 | 틀린 관계 |
|---|---|---|---|---|
| solar-pro3 | 76.9% | 30.7% | 75.0% | 20 |
| solar-pro4 + 경량 파이프라인 | 100% | 64.6% | 96.8% | 2 |

책 한 권 전체 분석 비용(pro4, 경계선 42개)은 정가 기준 약 $0.51이었다.

## 아직 남은 것

- 정답 세트 사람 검토, 그리고 관계 재현율이 63%에서 멈춘 원인 분석
- 인물 검사 기준값을 다른 책으로 검증
- 인물 검사와 호칭 연결을 넣은 상태로 책 전체 재분석 및 재채점
- 모든 인물의 중요도가 "minor"로 나오는 문제, `first_seen` 값이 비어 있는 문제
- 기대값을 새로 써야 하는 테스트 5개(skip 처리)
