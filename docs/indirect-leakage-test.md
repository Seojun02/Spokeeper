# 리마인드 스포일러·간접 누출 테스트 (Solar Pro 3 vs Pro 4)

IndirectLeakageJudge(구 3차 가드)를 유지할지 판단하기 위한 실험. 이 결과로 에이전트를 제거했다.
코드는 `eval/legacy/indirect_leakage_judge.py`, 실행은 `eval/remind_test.py`, 결과 원문은 `eval/results/remind_leak_test.json`.

## 방법
- 대상: 주홍색의 연구, 경량 파이프라인 결과(인물·관계)를 입력으로 오프셋 2·4·6·9·11장에서 ReminderWriter 실행.
- 같은 문장을 IndirectLeakageJudge에 통과시켜 전/후 비교. 사건(events)은 추출하지 않아 관계만으로 작성.
- 선제 스포일러 판정: 문장의 정보가 본문에서 처음 나오는 장과 오프셋을 대조(의심 표현은 본문 키워드로 확인).

## 결과
| | pro3 | pro4 |
|---|---|---|
| 작성된 문장 | 66 | 38 |
| 선제 스포일러 | 없음 | 없음 |
| 판정이 고친 문장 | 12 | 12 |
| 판정이 문장 수를 줄인 경우 | 0 | 2 (이미 본문에 나온 사실을 삭제) |

- 의심 표현 확인: "비서"(6장), "공범자"(5장), 변장(5장) 모두 해당 오프셋 이전에 본문에 나온 정보.
- pro3는 스포일러보다 관계 이름을 지어내는 문제(예: "범인-공범자", "하숙 동료-정보원")와 오프셋 9의 중복 문장이 컸고, 판정이 이를 해결하지 못했다.
- 판정이 고친 문장은 대부분 수식어 정리. **오프셋 11에서 판정이 오히려 "(이 탈출은 이후 사건의 발단이 됩니다.)"라는 복선 문구를 덧붙임.**

## 결론
- 이 샘플에서 판정 단계는 누출을 잡지 못했고 한 번은 누출을 만들었다. 호출 비용도 든다 → 제거.
- 한계: 5개 오프셋·두 모델·한 권. 사건 기반 리마인드는 미검증. 판정은 작성자가 직접 읽고 한 것이라 미묘한 암시를 놓쳤을 수 있음.
